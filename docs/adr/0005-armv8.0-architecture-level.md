# ADR 0005 — Starting architecture level: ARMv8.0-A (Cortex-A53)

- Status: accepted (M1, 2026-09-24)

## Context
Comparison with QEMU only makes sense if QEMU emulates the same CPU that
we declare to the guest. With `-cpu max` QEMU implements dozens of extensions
(LSE, PAuth, MTE, SVE, CSSC...): instructions that would be UNDEFINED for us
would be valid in the oracle, and vice versa.

## Decision
- Vetro starts from **ARMv8.0-A with the Cortex-A53 extensions**: CRC32,
  AdvSIMD/FP, AES/SHA1/SHA2/PMULL. No LSE, PAuth, MTE, SVE.
- The oracle always runs with `-cpu cortex-a53` (variable
  `VETRO_QEMU_CPU` to change it in experiments).
- The ID registers we will expose (M2/M3) describe exactly this
  level, so the guest does not use extensions we don't have.
- The decoder distinguishes two outcomes: `Undefined` (the architecture says
  UNDEFINED at this level) and `Unimplemented` (a valid instruction that we
  haven't written yet, e.g. SIMD/FP in M1). An `Unimplemented` is never
  confused with architectural behaviour.

## Consequences
Android 15 arm64 runs on ARMv8.0 (the libraries detect LSE at runtime). The
extensions are added one at a time, each with an ADR that raises the
oracle's QEMU model (e.g. `neoverse-n1` for v8.2).
