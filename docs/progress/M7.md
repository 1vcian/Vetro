## 2026-09-26 — TLS hooks: plaintext HTTPS in the HAR (Analysis agent, ADR 0029)
- **Done:** TLS hooks on top of the invisible breakpoints (ADR 0027).
  `vetro-machine::tls::TlsTracer` puts breakpoints on
  `SSL_write`/`SSL_read`/`SSL_write_ex`/`SSL_read_ex` of `libssl.so`
  resolved from each process's ELF symbols (system BoringSSL and
  Conscrypt's), captures the plaintext (SSL_write on entry, SSL_read
  on return via LR with a breakpoint set the first time it is seen),
  ties the connection to the 4-tuple from the `connect` fd on the same thread
  (`Linux::socket_endpoints` from `struct sock`, offsets from BTF:
  `layout::SockLayout`) and to process/library. `tls_service` installs the
  hooks of new processes between two quanta. Conversations become
  `vetro_analysis::net::TlsConversation` and `NetworkAnalysis::merge_tls`
  reconstructs them as `secure` HTTP requests with attribution, merged with
  the plaintext ones in the inspector (`view`: `secure`, `attribution`) and
  in the HAR (`_secure`, `_vetro`). `vetro boot --tls` (with `--har`/
  `--net-requests` and `--kernel-profile`). Snapshot at boot_completed:
  `vetro boot --save-on=TESTO:FILE [--save-delay=S] [--exit-after-save]`.
  Tests: unit (`net::tls`, `merge_tls` in the HAR, `socket_endpoints` via
  BTF), `vetro boot --tls` on the test kernel (profile loaded, hooks
  active, no crash; without libssl 0 conversations). Test app
  `tests/apps/vetro-probe` (HTTPS POST with JSON, built with the SDK).
- **Missing:** the sinkhole's TLS endpoint so that the app's connection
  completes (the sinkhole terminates TCP): primitives ready and verified with the
  RFC vectors but not integrated; to be done with the TLS 1.3 server, tested against
  `openssl s_client`, **or** the development CA in the image's trust store
  (AOSP rebuild, VM off) or the test app ignoring the
  certificate. Long test on Android from a snapshot (`VETRO_ANDROID=1`): 10
  apps with plaintext HTTPS tied to the action — not done yet (needs the
  snapshot at boot_completed and the TLS endpoint). Causal attribution
  to user input (with the timeline).
- **Blocked:** the M7 exit waits for the Android snapshot and the TLS
  endpoint (or the CA in the image). The build VM is off: the user

## 2026-11-15 — the gateway on the user's own computer, in Python (ADR 0050)
- **Done:** the owner ruled Cloudflare out (the free plan's CPU limit,
  quotas shared with his other projects, no route to sites behind
  Cloudflare), so the gateway now also exists as a program the user runs:
  `relay/py/` (`python3 relay/py/connect.py`; Python 3.10+, standard library
  only: asyncio, with the server side of RFC 6455 and a small HTTP/1.1
  written here). It is a port of `relay/src/` (frames, HTTP surface, tokens,
  ledger, lane logic, destination policy) and the page's `GatewayClient`
  uses it unchanged. It listens on 127.0.0.1 only (8787, or a free port),
  with a secret per run, for `https://1vcian.me` plus `--origin`; DNS comes
  from the system resolver (`getaddrinfo` off the event loop, local
  addresses left out of the answers); bandwidth and total bytes have no cap
  by default; starting it opens Chrome or Edge at
  `…/app/?gateway=http://127.0.0.1:PORT` and shows a small tkinter window
  (or the console) with the status and counters only, "Waiting for the page:
  allow the connection in Chrome if it asks" until the first session.
  Tests, all in `tools/web-test.sh`: 106 unit tests
  (`python3 -m unittest discover -s relay/py -t relay/py`, run with Python
  3.11 to 3.15 on the Mac); `node relay/test/python.mjs` (7 tests: the
  scenarios of `relay/test/node.mjs` with the page's client against the
  Python child process, tokens equal byte for byte to `token.mjs`'s);
  `node relay/test/python-online.mjs` (the BusyBox guest under vetro-wasm:
  DNS, a 600 KB GET, a refused private address);
  `node relay/test/python-browser.mjs` (the same in headless Chrome: the
  browser's `fetch` with its CORS preflight and its `WebSocket` against the
  hand-written server). 39 mutations (one safeguard or limit broken at a
  time, in a copy) are all caught. Measured on loopback, 64 MiB each way:
  675–761 MiB/s down and 275–283 MiB/s up (the Node gateway 413–418 and
  235–237 in the same harness). Packaging: `.github/workflows/connect.yml`
  with PyInstaller 6.22.3 and its tool chain pinned
  (`relay/py/build-requirements.txt`); a trial build on the Mac gave
  `Vetro Connect.app` (29 MB, 11 MB zipped), which starts and answers.
  Chrome's permission for a public page to reach the loopback address
  (`loopback-network`) was checked by hand on the live site with the Node
  gateway (Chrome 157: every request denied without it, everything works
  with it; ADR 0050). User guide: `docs/user/internet.md`, and the pages
  that described a gateway of ours now describe this one.
- **Missing:** the workflow has never run: there is no Windows executable,
  the program has never run on Windows, and no release is published (the
