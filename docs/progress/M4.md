## 2026-09-25 (JIT in system mode, JIT agent)
- **Done:**
  - System mode JIT (ADR 0013): `vetro_jit::sys::SysJit` and
    `Machine::set_jit`. Blocks keyed by (`pc`, EL, TBI0/1, SPSel), valid for the
    physical page of the fetch (retranslated at every entry from the host with the MMU
    and its recent-translation cache); host `ld`/`st` through `MmuBus` with the

## 2026-09-25 (JIT in user mode, JIT agent)
- **Done:**
  - `vetro-jit` (no dependencies, compiles for wasm32): WASM encoder,
    `JitState` with the offsets from the spec, translator, `Engine`/`Host` traits
    and `JitCpu`, which alternates translated blocks and interpreter steps.
  - Coverage: arithmetic and logic (immediate, register, extended, with
    carry, with flags), MOVZ/MOVN/MOVK, ADR/ADRP, bitfield, EXTR, CCMP/CCMN,
    CSEL and variants, RBIT/REV/CLZ/CLS, divisions and variable shifts,
    MADD/MSUB/SMADDL/UMADDL/SMULH/UMULH, MRS/MSR NZCV, all branches,
    integer LDR/STR (immediate, pre/post, register, literal), LDP/STP/LDPSW,
    LDAR/STLR. Left to the interpreter: SIMD/FP, exclusives, CRC32, DC ZVA,
    system registers other than NZCV, SVC/BRK (they close the block).
  - Precision: a fault in the middle of a block leaves the state from before
    the instruction, which the interpreter retries (same exception, same
    address). The step budget is exact: the emulated kernel asks the JIT
    for at most the steps up to the end of the quantum, the instruction limit and
    the next alarm deadline (virtual time), and only one if there is
    a signal to deliver. Same clock: same number of instructions
    with and without the JIT (202475874 for `sha256sum` of 4 MB).
  - Invalidation (design in `crates/vetro-jit/src/driver.rs`):
    `UserMemory` has a `space_id` (new at every copy, i.e. at every fork) and
    watches the pages the JIT has translated from; writes by the guest and
    by the emulated kernel (`write`, `poke`), mmap, munmap, mprotect, mremap and
    stack growth mark them dirty. The driver collects them
    before every block and after every interpreter step; a store from a
    block to a watched page exits with STOP after the instruction. Code
    in MAP_SHARED mappings is not translated. Compiled modules are reused
    across spaces by (pc, words).
  - ABI as in the updated spec on main: after every `ld` the block
    checks `exit_detail` (1 = FAULT, the answer to the Web agent's
    question), `st` leaves 2 for STOP; `pc` and `steps` are saved before every
    access.
  - `vetro-jit-native`: engine on wasmtime 49. wasmtime keeps at most 10000
    instances per store and does not free them: when `compile` fails the driver
    discards everything and calls `Engine::reset` (new store).
  - `vetro run --jit [--jit-threshold=N] [--stats]`,
    `Config { jit, jit_threshold }`; the tests/linux harnesses read
    `VETRO_JIT=1` and `VETRO_JIT_THRESHOLD`.
  - Parity (all with `VETRO_REQUIRE_ORACLE=1` and the Docker oracle):

## 2026-09-27 — FPSR.QC fixed (JIT agent)

- **Done:** the cause was the inline SQXTN(2)/SQXTUN(2) (ADR 0026): QC was set
  when the narrowed result differed from the truncated input, but a saturated
  lane can equal the truncation (0x017f -> 0x7f for SQXTN, 0x01ff -> 0xff for
  SQXTUN), so QC was missed. QC is now set when the result, widened back
  (sign-extended for SQXTN, zero-extended for SQXTUN), differs from the input.
  The inline [SU]Q{ADD,SUB} were already exact (a wrapped sum never equals the
  saturated one). New targeted test
  `vetro-jit-native` `saturating_simd_sets_qc_like_the_interpreter`
  (SQXTN/SQXTUN at both sizes with and without the "2" form, [SU]Q{ADD,SUB}
  at 8 and 16 bits, lanes around the limits; red with the old check). On the
  build VM with native QEMU 10 and `VETRO_REQUIRE_ORACLE=1`: seeds 3000056
  (`random_fp_focused`), 3002605 and 3015642 (`random_simd_programs`) red
  before, green after; `VETRO_DIFF_CASES=20000 VETRO_DIFF_SEED=3000000 cargo
  test --release -p vetro-diff -p vetro-isa-tests` green (135 tests, 0
  failures); `cargo test --release -p vetro-jit-native` green.

- **Harness:** `tools/aosp/android-perf.mjs` restores the app's prebuilt
  home-screen snapshot in Node/V8 on the app's machine and runs, phase by
  phase, what a visitor does: adb connect + screen on, 20 s of launcher idle,
  `adb push` + `pm install` of Flowit (catalog), `resolve-activity`,
  `am start -W`, focus, 20 s of app idle. Host actions depend only on the
  guest: every build runs exactly the same instructions per phase (checked:
  equal in all runs below), only the time changes. Wall and process CPU,
  disk wait (local block cache, R2 read once), JIT counters (new: host ld/st,
  epoch reasons, base switches, partial TLBIs, jump cache probes, WASM bytes),
  `Machine::perf` (interpreter steps, WFI skips, device services), class
  profile (`--profile`), `--cpu-prof`.
- **Profile before changes** (image bd09e2f, prebuilt 761 MiB, build VM
  shared at load 20-33, so wall times are inflated; counters are exact):
  - adb ready 31.5 s of guest time (3153 M instructions) took 509 s wall;
    launcher idle 20 s guest 288 s; `pm install` 25.4 s guest 517 s;
    `am start -W` 56.9 s guest 430 s. No WFI at all in any phase: the guest
    never idles (so a WFI skip has nothing to skip).
  - 1.14 M jump cache epochs in 31 s of guest time (TTBR0 switched at every
    kernel entry and exit by software PAN, each switch a new epoch and a full
    software TLB flush), 65 thousand more from TLBIs, 43 M `env.resolve`,
    39 M software TLB fills, 27 M/17 M host ld/st.
  - V8 CPU profile (adb phase, after the context fix): generated code 49%,
    host ld/st (TLB miss path) 9%, `Cache::lookup` 8%, interpreter 7%, glue

  - Interpreter classes (80 M steps in 51 s of guest time): 8 M LDTR/STTR

  permissions through the host); MRS TTBR0/1, CONTEXTIDR, MIDR, FPCR, FPSR and

  matches. Epochs in the adb phase: 1.14 M -> 1 (+197 TLBI, 1408 code).
