## 2026-09-24 (Network, preparation)
- **Done:** `vetro-net` from stub to host-side network stack (ADR 0007, spec
  `docs/specs/net.md`): virtual gateway like QEMU's user network (ARP,
  DHCP server 10.0.2.15/.2/.3, ICMP echo, port unreachable), TCP and UDP
  terminated host-side for each guest connection, `Upstream` trait with
  `Sinkhole` (records connections and bytes, per-port responses, DNS to
  fake addresses 198.18.x.y in query order) and `RelayUpstream` +
  `MemoryRelay` (interface and in-memory test only), event log with
  virtual time. Deterministic (time as a parameter, ISN from the seed,
  `BTreeMap`), no runtime dependencies; `smoltcp::wire` only in tests
  as an independent parser. 34 tests green (`cargo test -p vetro-net`),
  clippy, fmt and wasm32 build green. Simultaneous transfer in both
  directions was also tested by hand on 2000 seeds with 30% and 45%
  frame loss (unlimited retransmissions): everything delivered and cleanly closed;
  12 seeds at 20% run in CI. Found and fixed along the way: a zero-window
  probe that put a byte in flight (now an empty segment with an
  already-acknowledged sequence, as in Linux) and an RTO that stayed doubled after
  a burst of losses (now an ACK of new data brings it back to the
  computed value, as in BSD/Linux), both with tests.
- **Missing:** connection to virtio-net (Platform agent: `receive` for
  each guest frame, `pop_frame` towards the guest, `poll` at
  `next_deadline`; do not offer `VIRTIO_NET_F_CSUM`); test with a real Linux
  kernel (udhcpc, wget, nslookup); IPv6 and IPv4 fragments not handled
  (documented); real WebSocket relay, message encoding and host↔relay flow
  control (M7); serializable state for snapshots (M6).
- **Blocked:** nothing.

## 2026-09-25 (CPU agent: system mode speed)
- **Done:** cache of recent translations in the `Mmu` (one entry per TLB slot, valid as long as the slot does not change and the translation registers are the same: result identical to the full path, even without TLBI) used by `MmuBus`; aligned fetch in `SysMem` without the generic path (fixed-length 4-byte physical read); FP/SIMD check with `fp_trapped` first. Kernel boot (`tests/boot --test vetro`, 98439742 instructions, log identical to QEMU), on M2 Pro: before 9.7 s (10.2 MIPS, 32.7 G cycles), after 8.2 s (12.0 MIPS, 27.9 G cycles). Tests: random equivalence cache/full path (4 seeds, 120 000 steps, with TLBI, table changes, TTBR/ASID, TCR, MAIR, SCTLR), TLBI/TTBR/ASID, permissions/Device/MAIR, TLB eviction; in `tests/system.rs` self-modifying code, code remapped with TLBI, change of TTBR0 and ASID, fetch from EL0 on a page executed at EL1. Measured and discarded (no gain): per-word decode cache, fixed-length data reads/writes.
- **Missing:** the real bottleneck is outside CPU/MMU: `Env::irq_line` in `vetro-machine/src/board.rs` calls `Gic::irq_line`, which scans all interrupts, before every instruction with IRQs unmasked (66% of the time). With a cached level in the `Board` (cleared on MMIO, ICC_*, `update_irqs`, virtio) the boot drops to 3.5 s without the CPU/MMU optimizations and to 2.0 s (49 MIPS, 6.8 G cycles) with them: 4.8 times the baseline, same instructions and same log. Then: `RefCell` for every physical access in `Phys` (1.5-3%), LTO in the release profile (−6% cycles, ADR).
- **Blocked:** the change to `board.rs` and to the profile in `Cargo.toml` is not in the CPU agent's folders: the owner of `vetro-machine` is needed (patch ready, measured above).
